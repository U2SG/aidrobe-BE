# AI 通勤穿搭助手：技术方案草案

## 1. 目标

为 V1 提供可实现、可扩展的技术路线，重点回答三个问题：

1. 图像是否要存，如何存
2. 图片信息如何提取
3. 推荐展示用文字、真实单品图还是生图

---

## 2. 图像存储方案

## 2.1 结论
不要只存标签，建议采用“三层存储”：

1. 图像层
2. 结构化标签层
3. embedding 层

## 2.2 图像层
### 建议保存
- original_image_url：原图
- cover_image_url：压缩展示图
- 可选：mask / cutout / thumbnail

### 原因
- 未来可重跑模型
- 允许更强识别与风格提取
- 便于后续拼搭板和视觉增强

## 2.3 结构化标签层
- category
- sub_category
- color
- season
- style_tags
- formality
- status
- location

## 2.4 embedding 层
用于：
- 相似单品检索
- 风格聚类
- 外部灵感映射
- 召回候选单品

---

## 3. 存储实现建议

## 3.1 对象存储
图片存对象存储：
- S3 / R2 / Supabase Storage 均可

## 3.2 元数据存储
结构化字段存 PostgreSQL。

## 3.3 向量存储
### V1
可直接用 pgvector。

### V2+
若检索量上来，可替换为独立向量数据库。

---

## 4. 图片理解链路

## 4.1 V1 推荐思路
使用“检测 / 分割 + 属性抽取 + embedding”的组合，而不是一个模型包打天下。

## 4.2 链路
1. 图片上传
2. 图片预处理
3. 衣物区域检测 / 分割
4. 分类与属性识别
5. 颜色提取
6. embedding 生成
7. 输出候选属性给确认页

## 4.3 V1 原则
- 先做品类与颜色
- 允许用户手动修正
- 不追求一次性全自动高精度

---

## 5. 推荐展示方案

## 5.1 V1 方案
真实单品图 + 文字解释

## 5.2 原因
- 幻觉风险最低
- 用户信任度高
- 成本最低
- 最贴近“能不能现在穿”的目标

## 5.3 不建议 V1 作为主链路的方案
用户上身生图 / 虚拟试穿

### 原因
- 容易失真
- 需要额外的人体图
- 隐私成本更高
- 算法成本更高
- 对当前核心目标帮助有限

## 5.4 演进路线
- V1：真实单品图卡片
- V2：自动拼搭板
- V3：可选虚拟试穿

---

## 6. 推荐引擎架构

## 6.1 结论
推荐引擎不要直接把全量衣橱交给 LLM，自由生成搭配。

## 6.2 建议架构
规则过滤 + 候选生成 + 打分排序 + LLM 文案解释

## 6.3 流程
1. 获取可穿衣物
2. 规则生成 outfit candidates
3. 对候选组合打分
4. 挑出三套
5. 用 LLM 生成推荐理由

## 6.4 评分维度
### V1
- 品类完整度
- 颜色协调度
- 基础正式度
- 状态可穿性
- 位置可执行性（粗粒度）

### V2
- 天气匹配
- 场景匹配
- 用户偏好
- 最近穿着频次
- 重复控制

## 10. 技术优先级建议

## 第一优先级
- 图片上传与存储
- 结构化衣物表
- 基础识别链路
- 推荐候选生成与展示

## 第二优先级

- 链接导入
- 埋点
- 推荐理由生成

## 第三优先级
- 天气接入
- 向量相似检索增强
- 拼搭板
- 外部灵感映射

---

## 11. 技术决策一句话总结

不要做成“拍图 -> 打标签 -> LLM 自由发挥 -> 生图展示”的链路。  
更合理的路线是：

拍图 / 导入 -> 图像 + 标签 + embedding 入库 -> 规则召回候选 -> 排序 -> 用真实单品图与文案向用户展示。
