# 尺寸与合身度系统设计

> 文档编号：15  
> 文档版本：V1.0  
> 适用范围：Aidrobe V1–V4 产品演进、衣物入库、推荐系统、用户反馈、Style Profile、Fit Profile  
> 核心主题：如何在不增加用户负担和不冒犯用户的前提下，让尺寸、合身度和体型变化服务于穿搭推荐。

---

## 1. 背景与问题定义

衣服的尺寸不是单纯的库存字段。对于 Aidrobe 来说，它同时影响：

```text
合身度
舒适度
风格判断
推荐可信度
用户是否真的会穿
```

同一件衣服，不同尺寸或不同穿着方式，可能代表完全不同的风格：

| 单品 | 合身状态 | 可能表达的风格 |
|---|---|---|
| 白衬衫 | 合身 | 通勤、利落、正式 |
| 白衬衫 | 宽松 | 松弛、韩系、休闲 |
| 西装外套 | 合身 | 职业、正式、稳妥 |
| 西装外套 | oversized | 时髦、松弛、有造型感 |
| 针织衫 | 修身 | 精致、女性化、轻熟 |
| 针织衫 | 宽松 | 舒适、慵懒、日常 |

所以 Aidrobe 不应只设计一个简单的 `size = M` 字段，而应该建立一套围绕衣物的 **Fit System**。

核心原则：

> 尺码是参考，合身度才是推荐系统真正关心的信号。

---

## 2. 产品结论

### 2.1 V1 不强制录尺寸

V1 的核心目标是降低录入成本，跑通“录入衣服 → 每日推荐 → 用户采用 → 反馈”的闭环。

如果一开始要求用户填写：

```text
身高、体重、肩宽、胸围、腰围、臀围、衣长、袖长、裤长
```

用户会感到麻烦，甚至会因为身体数据敏感而放弃。

V1 只做轻量字段：

```text
尺码：可选
穿着感：未知 / 合身 / 偏宽松 / 偏紧
```

### 2.2 V2 引入合身度反馈

用户穿完一套之后，轻量询问：

```text
这套穿起来怎么样？
[舒服] [有点紧] [有点松] [活动不方便] [不想再穿]
```

这比单纯点赞更有价值。

### 2.3 V3 建立 Fit Profile

系统从用户反馈中学习：

```text
上衣喜欢宽松
裤子喜欢直筒
不喜欢太紧
喜欢高腰
喜欢遮胯
偏好舒适优先
```

### 2.4 V4 处理体型变化和衣橱整理

体型变化不应该直接问用户“体重变了吗”，而应该围绕衣物提问：

```text
这件最近穿起来还合身吗？
[合身] [偏紧] [偏松] [暂时不推荐]
```

## 3. 为什么不能只存 size_label

### 3.1 尺码没有统一标准

同样是 M 码，不同品牌、不同国家、不同款式可能差别很大。

例如：

```text
Zara 的 M
优衣库的 M
淘宝女装的 M
美码 6
欧码 38
160/84A
```

这些不能直接用于推荐判断。

### 3.2 尺码不等于风格

`M` 本身不是风格，但“这件衣服穿在用户身上的状态”是风格。

真正有价值的是：

```text
regular / fitted / relaxed / oversized / cropped / longline
```

### 3.3 尺码不等于当前是否可穿

用户可能买的是 M，但现在：

- 穿起来偏紧
- 穿起来偏松
- 已经不合身
- 原本就是 oversized 风格
- 需要改裤长

所以需要拆成多层字段。

## 4. 尺寸系统的四层模型

Aidrobe 的尺寸与合身度系统建议拆成四层。

### 4.1 Size Label：吊牌尺码

衣服购买或吊牌上的尺码。

示例：

```text
S / M / L / XL
36 / 38 / 40
160/84A
27 / 28 / 29
US 6 / EU 38
```

用途：

- 作为衣物档案信息
- 从电商订单或商品链接中自动提取
- 供用户查找和确认
- 作为合身度判断的弱信号

局限：

- 不同品牌差异大
- 不同版型差异大
- 不能单独决定是否推荐

---

### 4.2 Garment Measurements：衣物实测尺寸

衣服本身的实际尺寸。

字段示例：

```text
shoulder_width
bust
waist
hip
length
sleeve_length
inseam
unit
```

来源：

```text
manual：用户手动填写
product_page：商品详情页解析
ai_extracted：从商品图/尺码表识别
```

使用建议：

- V1 不强制
- V2/V3 从商品链接、订单截图、商品详情图中自动提取
- 高级用户可以手动补充

---

### 4.3 Fit Intent：穿着意图

这件衣服设计上或用户穿着上想表达的版型风格。

枚举建议：

```text
regular       正常合身
fitted        修身
relaxed       松弛
oversized     宽松廓形
cropped       短款
longline      长款
wide_leg      宽腿
straight      直筒
slim          修身窄版
```

为什么重要：

```text
loose + fit_intent=oversized → 这是风格
loose + fit_intent=regular → 可能是不合身
```

对推荐的影响：

- `oversized` 可以增强松弛感、韩系感、时髦感
- `fitted` 可以增强精致感、正式感、女性化
- `relaxed` 可以增强舒适度、低压力、日常感
- `cropped` 可以影响比例优化
- `wide_leg` 可以影响下装风格和鞋子选择

---

### 4.4 Fit Status：当前合身状态

这件衣服现在穿起来是否适合用户。

枚举建议：

```text
unknown           未确认
fits_well         合身
loose             偏松
tight             偏紧
oversized_ok      宽松但符合风格意图
needs_alteration  需要修改
no_longer_fits    已不合身
```

对推荐的影响：

| Fit Status | 推荐策略 |
|---|---|
| fits_well | 正向加权 |
| oversized_ok | 根据风格场景加权 |
| loose | 轻微降权或结合 fit_intent 判断 |
| tight | 降权，赶时间时进一步降权 |
| needs_alteration | 默认不推荐或低权重 |
| no_longer_fits | 硬过滤 |
| unknown | 中性处理，必要时提示用户确认 |

## 5. 用户体型变化如何处理

### 5.1 不要直接围绕身体提问

不建议这样问：

```text
你是不是胖了？
你体重变了吗？
请更新体重。
```

这会冒犯用户，也会增加隐私压力。

### 5.2 应该围绕衣服提问

更好的表达是：

```text
这件最近穿起来怎么样？
[合身] [有点紧] [有点松] [暂时不想穿]
```

这把“体型变化”转化为“衣物状态变化”。

### 5.3 系统推断方式

当系统观察到：

```text
最近多件裤装被反馈偏紧
最近修身上衣频繁被跳过
某类衣服长期不被采用
```

可以推断：

```text
用户当前可能更偏好宽松或舒适版型
```

但产品表达上应该说：

```text
最近你经常跳过修身裤，要不要减少类似推荐？
```

不要说：

```text
你最近是不是体型变了？
```

## 6. Fit Feedback：合身度反馈机制

### 6.1 触发时机

#### 触发时机一：用户选择“今天穿这套”之后

可以在当天晚些时候或下次打开 App 时轻问：

```text
这套穿起来怎么样？
```

#### 触发时机二：用户点“不喜欢”之后

原因标签加入：

```text
有点紧
有点松
不舒服
显得比例不好
活动不方便
```

#### 触发时机三：某件衣服长期未被使用

```text
这件已经 60 天没穿了，还合身吗？
```

#### 触发时机四：换季整理

```text
换季前要不要快速检查几件常用单品是否还合身？
```

### 6.2 反馈选项

单件衣物反馈：

```text
合身
偏紧
偏松
不舒服
需要修改
暂时不推荐
```

整套穿搭反馈：

```text
舒服
有点紧
有点松
活动不方便
比例不好
不想再穿
```

场景反馈：

```text
今天上班合适
太正式
太休闲
不适合走路
不适合久坐
```

## 7. 推荐系统如何使用 Fit 信息

### 7.1 硬过滤

以下情况不进入推荐：

```text
fit_status = no_longer_fits
fit_status = needs_alteration 且未修正
status = unavailable
status = stored_off_season
```

### 7.2 降权

以下情况降低推荐分：

```text
fit_status = tight
fit_status = loose 且 fit_intent != oversized
comfort_score 较低
fit_confidence 较低
```

赶时间时，进一步降低：

```text
偏紧
需要调整
穿脱麻烦
活动不方便
```

### 7.3 加权

以下情况增加推荐分：

```text
fit_status = fits_well
comfort_score 高
历史多次穿着
穿后反馈舒服
符合用户 preferred_fit
```

### 7.4 影响风格判断

Fit 信息不仅影响能不能穿，也影响风格表达。

| Fit Intent | 风格影响 |
|---|---|
| fitted | 精致、正式、显身材 |
| regular | 稳妥、日常、通勤 |
| relaxed | 舒适、低压力、自然 |
| oversized | 松弛、韩系、时髦 |
| cropped | 拉高比例、轻盈 |
| wide_leg | 松弛、复古、修饰腿型 |

## 8. Fit Score 评分模型

推荐评分中建议加入 `fit_score`。

### 8.1 V2 评分公式

```text
final_score =
  aesthetic_score * 0.25
+ execution_score * 0.25
+ fit_score * 0.20
+ context_score * 0.15
+ freshness_score * 0.15
```

### 8.2 Fit Score 组成

```text
fit_score =
  current_fit_status_score
+ comfort_feedback_score
+ preferred_fit_match_score
+ scene_fit_match_score
- tight_penalty
- alteration_penalty
```

### 8.3 场景差异

| 场景 | Fit 加权策略 |
|---|---|
| 普通通勤 | 合身、舒适优先 |
| 重要会议 | 合身、利落、正式加权 |
| 赶时间 | 舒服、不需要调整加权 |
| 约会 | 用户偏好的修身/显身材/氛围感加权 |
| 周末 | relaxed / oversized 加权 |
| 长时间步行 | 舒适、活动方便加权 |

## 9. 数据结构设计

### 9.1 wardrobe_items 字段扩展

```text
size_label              // M / L / 38 / 160/84A
size_region             // CN / US / EU / JP / brand_specific
fit_intent              // regular / fitted / relaxed / oversized / cropped / longline
fit_status              // unknown / fits_well / loose / tight / oversized_ok / needs_alteration / no_longer_fits
comfort_score           // 1-5
fit_confidence          // low / medium / high
last_fit_checked_at     // 最近一次确认合身状态时间
```

### 9.2 garment_measurements

衣物实测尺寸建议单独建表，不要塞进 `wardrobe_items`。

```text
garment_measurements
- id
- item_id
- shoulder_width
- bust
- waist
- hip
- length
- sleeve_length
- inseam
- unit                  // cm / inch
- source                // manual / product_page / ai_extracted
- confidence_score
- created_at
- updated_at
```

原因：

- 并非每件衣物都有完整尺寸
- 电商导入时可能获得部分字段
- 手动填写成本高，不应污染主表

### 9.3 user_fit_profile

用户侧不要叫 `body_profile`，建议叫 `fit_profile`，降低敏感感。

```text
user_fit_profile
- user_id
- preferred_top_fit          // fitted / regular / relaxed / oversized
- preferred_bottom_fit       // slim / straight / wide_leg / loose
- preferred_waist_rise       // high / mid / low
- preferred_length_tags      // cropped / regular / longline
- avoid_fit_tags             // too_tight / too_short / too_long / low_rise
- comfort_priority           // low / medium / high
- updated_at
```

这是用户偏好，不是身体数据。

### 9.4 fit_feedback

```text
fit_feedback
- id
- user_id
- item_id
- outfit_id
- feedback_type             // fits_well / tight / loose / uncomfortable / easy_to_move / not_flattering
- scene                     // commute / formal / casual / date / travel
- created_at
```

用途：

- 更新 `fit_status`
- 更新 `comfort_score`
- 训练 `user_fit_profile`
- 降低不适合衣物推荐权重

## 10. 电商导入与尺寸

商品链接、订单截图、购物记录中常见：

```text
颜色：米白
尺码：M
规格：高腰直筒 / 160/66A
版型：宽松 / 修身 / 直筒
```

这些信息可以自动进入：

```text
size_label
sku_color
sku_size
fit_intent
product_size_info
garment_measurements
```

导入确认页可以轻问：

```text
这件尺码是 M，对吗？
穿着感是？
[还没穿] [合身] [偏大] [偏小]
```

这样既利用了电商数据，又不强迫用户手填。

## 11. 与 Style Profile 的关系

尺寸本身不是风格，版型偏好才是风格。

不要在 Style Profile 里记录：

```text
喜欢 M 码
```

应该记录：

```text
上衣偏宽松
下装喜欢直筒
不喜欢太紧
喜欢高腰
喜欢短外套拉高比例
偏好舒适优先
```

Fit Profile 可以作为 Style Profile 的子模块：

```text
style_profile
├── color_preference
├── silhouette_preference
├── formality_preference
├── fit_profile
└── avoid_tags
```

## 13. 隐私与敏感性边界

### 13.1 默认不收集身体数据

V1/V2 默认不要求用户填写：

```text
体重
胸围
腰围
臀围
身体照片
```

默认只收集：

```text
衣物尺码
穿着感
偏好版型
是否合身
```

### 13.2 高级功能必须用户主动开启

如果未来提供高级合身推荐，可选收集：

```text
身高
体重范围
身体尺寸
全身照
```

但必须满足：

- 明确告知用途
- 可跳过
- 可删除
- 可关闭
- 不影响基础推荐使用

### 13.3 产品表达原则

围绕衣服，不围绕身体。

正确表达：

```text
这件最近穿起来还合身吗？
```

错误表达：

```text
你的身材变了吗？
```

## 14. 版本规划

### V1：可选尺寸字段

- 导入确认页增加可选 `size_label`
- 增加可选 `fit_status=unknown / fits_well / loose / tight`
- 不参与强推荐，仅用于记录

### V2：合身度反馈进入推荐

- 增加穿后 fit feedback
- 将 `fit_status=no_longer_fits` 作为硬过滤
- 将 `tight / needs_alteration` 降权
- 增加 `comfort_score`

### V3：Fit Profile

- 学习用户偏好的上衣/下装版型
- 推荐理由可引用版型偏好
- 支持“少推荐太紧的下装”
- 支持“更宽松 / 更修身”微调

### V4：体型变化与衣橱整理

- 长期未穿衣物合身度检查
- 换季合身度检查
- 多件反馈偏紧/偏松时的轻提醒
- 高级用户可选身体数据或全身照
- 与虚拟试穿和购物前评估结合

## 16. 验收指标

### 使用指标

- 尺码字段填写率
- 穿着感字段填写率
- fit feedback 提交率
- 合身度检查完成率

### 推荐指标

- 加入 fit_score 后推荐采用率变化
- 偏紧/不舒服反馈下降率
- `no_longer_fits` 衣物误推荐率
- 用户主动修改 fit_status 的频率

### 体验指标

- 用户是否觉得问题冒犯
- 合身度反馈是否影响留存
- 衣橱整理提醒是否被接受

## 17. 结论

Aidrobe 应该记录尺寸，但不应该把尺寸变成用户负担。

最合理的设计不是：

```text
请填写你的身体数据和每件衣服的详细尺寸。
```

而是：

```text
这件衣服现在穿起来怎么样？
```

最终系统应该形成五类信息：

```text
size_label      作为可选记录
fit_intent      作为风格信号
fit_status      作为推荐约束
fit_feedback    作为学习数据
fit_profile     作为长期偏好
```

这套设计能同时处理：

- 不同尺码带来的风格差异
- 当前是否合身
- 用户体型变化
- 穿着舒适度
- 推荐可信度
- 隐私和敏感性边界

一句话总结：

> Aidrobe 不应该问用户“你变了吗”，而应该帮助用户判断“这件衣服现在还适合你吗”。
