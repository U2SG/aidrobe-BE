# 设计会话接续与体验记录

## 本轮目标

在第一版真实搭配闭环上，接入可以提前开发、独立验证的三项能力：

1. 从正在讨论的设计进入购买判断或旅行打包，并带着结果回到原对话。
2. 分开记录“觉得好看”“想试试”和实际穿着后的感受。
3. 把已经完成真实图像分析的灵感用于一次新设计。

本轮复用已有购买、打包、穿着和视觉分析服务。模型不会自行购买商品、安排旅行或把试穿意愿写成实际穿着。

## 购物与旅行接续

- V3 购买判断和创建打包清单接受 `design_context: {conversation_id, expected_revision}`。
- 服务端校验账号和版本，保存 `conversation_id/revision/outfit_id/constraints` 快照。已有条件待生成新搭配时，仍传递最新条件，但 `outfit_id` 为 null。
- 排除与锁定单品参与实际候选处理；目标风格与当前搭配参与优先选择。无法保留锁定单品时明确返回冲突，不静默放弃条件。
- 旅行请求自己的日期和场合用于旅行规划；原设计的临时偏好例外只在日期和场合都对应时使用。
- 购买判断沿用候选的幂等身份；同一结果不能冒充另一个设计版本的判断。旅行请求通过 `request_id` 幂等，同一请求重试返回原结果。
- 结果以 `linked_result` 写入原会话，包含种类、真实资源 ID、源版本和摘要。客户端可以打开已有结果或回到原对话。
- 后续 Ask 动态读取仍存在、仍可访问的结果；业务开关关闭或源资源删除后，结果不再进入模型上下文。动态来源不进入持久对话摘要。

V2 sense-check 保留既有入口，本轮设计接续使用 V3 购买判断。

## 体验记录

`/v1/styling-experiences` 提供记录、读取与撤销；记录绑定真实 Outfit，因此绑定的是实际搭配版本。

| kind | 含义 | 是否代表穿过 |
|---|---|---|
| appreciated | 欣赏这一套的视觉效果 | 否 |
| want_to_try | 有意愿尝试这一套 | 否 |
| wear_feedback | 对一次真实穿着的感受 | 必须有对应日期的 WearHistory |

- 穿后感受支持 `like/neutral/dislike`、场合和备注。
- `request_id` 防止重复提交；撤销后保留幂等记录，旧请求重试不会复活数据。
- 更正通过 `supersedes_id` 在同一事务中替换原记录。同一套搭配、同一意图仅有一条活跃记录；穿后感受另外按穿着日期区分。
- 这些记录不直接写入长期偏好。Ask 读取有界的近期经历，明确区分欣赏、意愿和真实体验。
- 撤销、更正和清空 Memory 的上下文水位共同约束后续读取。已开始但较晚完成的回答不能重新填回被撤销的摘要或偏好。
- 按 Outfit 读取时保留当前两种意图，再填近期穿后记录，避免多次穿着把仍有效的意图状态挤出列表。

## 灵感参考

- `InspirationResponse.design_reference_available` 仅对已完成真实视觉分析的图片为 true；域名猜测、排队中或分析失败均不算可用。
- 客户端从灵感库选择“照这个感觉搭”，预填问题并打开新设计，等用户发送。
- `StylingConstraints.reference_inspiration_id` 保存来源 ID。每轮按当前用户重新读取有效分析，不持久保存签名 URL，也不把图中衣物当成用户衣橱。
- 现阶段使用真实分析提供的风格标签、配色和置信度，进入提示词与衣橱候选排序。尚不支持从这些标签推断版型、面料、合身程度。
- 本次选择不会新增长期偏好；灵感库原有的学习行为与这次设计引用是不同动作。
- 已选图片后来不可用时，会话仍可按已确认条件继续，模型不得声称仍看到了该图。

## 数据与启用

- `0057_styling_experiences` 新增有撤销记录的体验表。
- `0058_design_continuity` 为打包清单增加设计上下文与请求幂等字段。
- 降级不得静默丢失已保存的体验或接续数据。
- 公共基础开关为 `ENABLE_DESIGNER_SESSIONS`；设计问答还需要 `ENABLE_ASK_TOOLS`、`ENABLE_ASK_STRUCTURED_OUTPUT` 和支持工具调用的 provider。
- 购物、旅行与参考图分别尊重 `ENABLE_V3_PURCHASE_DECISION`、`ENABLE_PACKING_LIST`、`ENABLE_VISION_STYLE_LEARNING`。逐日旅行计划继续由 `ENABLE_PACKING_PLANNER` 控制。
- OpenAPI 由服务代码生成；iOS 契约固定到本轮真实后端提交。

## 验证边界

GitHub CI 覆盖权限、版本、重复请求、待更新条件、来源删除、Memory 撤销和接口契约。自动化使用可控模型与数据验证协议，不能证明真实模型审美质量。

实际验收还需依次完成：

1. 真实衣橱设计 → 查看拟购单品 → 返回同一对话继续修改。
2. 当前设计 → 不同日期的旅行 → 逐日条件与锁定单品保持正确 → 重开已有清单。
3. 好看 → 想试 → 记录穿着 → 穿后反馈 → 更正或撤销；验证 Today 与 Memory 没有把不同阶段混为一谈。
4. 真实灵感图分析 → 发起设计 → 看实际选衣变化 → 删图后继续。
5. 退出、重开、切换账号、慢请求和网络失败；分别检查 iOS 与 RN。

长期风格演进、完整图像语义理解、统一自动业务编排以及真实人像试穿仍是后续范围。
