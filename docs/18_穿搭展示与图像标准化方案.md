# 穿搭展示与图像标准化方案

> 文档编号：14  
> 文档版本：V1.0  
> 适用范围：Aidrobe V1–V4 产品演进、推荐页展示、图片处理服务、视觉资产系统  
> 核心主题：如何用用户真实衣物，生成可信、好看、可执行的穿搭视觉结果

---

## 1. 背景与问题定义

Aidrobe 的核心场景不是“让 AI 画一张漂亮穿搭图”，而是帮助用户在出门前快速做出穿搭决策。

因此穿搭展示系统需要同时满足三个目标：

```text
真实可信：展示的是用户真的拥有的衣物，而不是模型臆造的衣服。
视觉好看：不能只是枯燥清单，需要让用户一眼看出搭配感。
现实可执行：必须告诉用户这几件衣服在哪里、是否可穿、是否来得及。
```

如果默认把用户衣服图、鞋图、Style Profile 全部喂给生成式模型来生图，会遇到四个问题：

1. **成本高**：每次推荐都需要处理多张图片，推理成本和延迟都高。
2. **幻觉风险高**：模型可能改变衣服颜色、版型、长度、材质。
3. **信任损耗大**：生成图好看但和真实衣服不一致，会破坏用户对推荐的信任。
4. **主任务偏移**：用户早晨真正需要的是“现在穿哪套”，不是欣赏一张 AI 海报。

所以 Aidrobe 的视觉表达应遵循：

> 优先使用用户真实衣物图，先做可信展示，再做风格化表达，最后再提供可选生图或虚拟试穿。

---

## 2. 总体策略

Aidrobe 的穿搭展示采用四层演进：

| 阶段 | 展示方式 | 核心价值 | 是否默认展示 |
|---|---|---|---|
| V1 | 真实单品图卡片 | 最快落地、最低幻觉、最可信 | 是 |
| V2 | 真实衣物抠图拼搭板 | 提升搭配感和视觉完成度 | 是 |
| V3 | Style Profile 风格化拼搭板 | 展示也体现用户审美 | 是 |
| V4 | 用户主动触发的生图 / 虚拟试穿 | 提供上身参考和高级体验 | 否，用户主动触发 |

核心原则：

```text
推荐主链路不默认生图；
生图能力作为可选增强，不作为可信展示基础；
真实衣物图、抠图图和拼搭板是默认视觉资产。
```

## 3. V1：真实单品图卡片

### 3.1 目标

让用户在几秒内看懂推荐方案，并确认这套衣服真实存在、可找到、能执行。

### 3.2 展示内容

每套穿搭卡片包含：

- 方案名称：最稳妥 / 最省时间 / 更有风格感
- 单品缩略图：上衣、下装、外套、鞋、包等
- 推荐理由
- 时间标签：宽裕 / 标准 / 紧张 / 极速
- 取衣提示：主衣柜、抽屉、鞋柜等
- 操作按钮：今天穿这套 / 不喜欢 / 换一套 / 查看详情

### 3.3 示例结构

```text
[最省时间]
白色衬衫 + 黑色直筒裤 + 乐福鞋

理由：这几件都处于可穿状态，主要单品在主衣柜和鞋柜，适合今天快速出门。

[今天穿这套] [不喜欢]
```

### 3.4 优点

- 工程成本低
- 不依赖生成式图像模型
- 用户信任度高
- 适合 MVP 验证

### 3.5 缺点

- 视觉表现偏工具化
- 搭配整体感不如拼搭板
- 不足以形成强视觉差异化

---

## 4. V2：真实衣物抠图拼搭板

### 4.1 目标

在不牺牲真实性的前提下，让推荐结果更像一套完整穿搭，而不是单品列表。

### 4.2 核心方式

对每件衣物生成 `cutout_image_url`，去除背景后自动排成 Outfit Board。

推荐链路：

```text
衣物入库
→ 主体检测
→ 背景分割
→ 生成透明 PNG
→ 保存 cutout_image_url
→ 推荐生成 outfit
→ 根据品类和角色自动排版
→ 输出 outfit_board_image_url
```

### 4.3 拼搭板基础布局

#### 通勤基础布局

```text
      外套
  上衣      包
      下装
      鞋
```

#### 快速出门布局

```text
[上衣] + [下装] + [鞋]
```

#### 连衣裙布局

```text
  外套
  连衣裙
  鞋 / 包
```

### 4.4 排版规则

| 单品角色 | 默认位置 | 尺寸优先级 |
|---|---|---|
| outerwear | 上方或左上 | 大 |
| top | 中上 | 中 |
| bottom | 中下 | 中 |
| dress | 中央 | 大 |
| shoes | 底部 | 小 |
| bag | 右侧 | 小 |
| accessory | 辅助角落 | 小 |

### 4.5 优点

- 使用真实衣物，不改变版型和颜色
- 视觉完成度明显高于列表卡片
- 可缓存，可批量生成
- 成本远低于生图
- 适合成为推荐页默认视觉形态

### 4.6 失败兜底

如果某件衣服暂无抠图图：

```text
cutout_image_url 不存在
→ 使用 thumbnail_url
→ 若 thumbnail_url 不存在，使用 normalized_image_url
→ 若仍不存在，使用占位图 + 单品名称
```

## 5. V3：结合 Style Profile 的风格化拼搭板

### 5.1 目标

让展示方式不仅表达“这套能穿”，还表达“这套像你”。

### 5.2 Style Profile 的展示用途

Style Profile 不应该只影响推荐排序，也应该影响视觉呈现。

| 用途 | 说明 |
|---|---|
| 推荐排序 | 调整颜色、正式度、廓形、风格偏好权重 |
| 展示模板 | 选择拼搭板背景、字体风格、信息密度 |
| 推荐解释 | 让理由引用用户偏好，而不是泛泛描述 |
| 微调入口 | 支持“更正式 / 更轻松 / 更省事 / 更有风格” |

### 5.3 模板示例

#### 极简通勤模板

适用画像：`minimal / commute / neutral_colors / clean_fit`

展示特征：

- 大留白
- 米白或浅灰背景
- 文案简短
- 强调“干净、利落、稳妥”

#### 温柔轻熟模板

适用画像：`soft / feminine / korean / pastel`

展示特征：

- 柔和背景
- 更强配色说明
- 文案强调“温柔、轻盈、清爽”

#### 成熟正式模板

适用画像：`formal / classic / elegant / office`

展示特征：

- 信息密度略高
- 强调正式度和场景匹配
- 突出会议、见客户、工作日适配

### 5.4 推荐解释示例

普通理由：

```text
这套颜色协调，适合通勤。
```

Style Profile 增强后：

```text
这套延续了你常喜欢的黑白灰通勤风格，整体干净利落；主单品都在主衣柜，适合今天快速出门。
```

## 6. V4：可选生图 / 虚拟试穿

### 6.1 目标

为高意愿用户提供更强的上身参考、风格探索和会员价值。

### 6.2 使用边界

生图 / 虚拟试穿不作为推荐主链路，而是用户主动触发：

```text
用户查看某套详情
→ 点击“看看上身效果”
→ 进入异步生成任务
→ 生成完成后缓存结果
```

### 6.3 适合场景

- 重要会议前想确认整体效果
- 约会 / 周末 / 聚会等非高压场景
- 用户对某套搭配犹豫
- 会员功能
- 风格探索

### 6.4 不适合场景

- 每天早上默认为三套都生成
- 推荐列表中强依赖生成图
- 用生成图替代真实衣物图
- 在没有用户主动授权全身照的情况下做试穿

### 6.5 产品提示

虚拟试穿必须明确标注：

```text
AI 效果图仅供搭配氛围参考，实际版型、长度和质感以真实衣物为准。
```

## 7. 用户拍摄质量问题

用户拍摄图片会直接影响：

- 衣物识别准确率
- 颜色判断
- 背景分割效果
- 拼搭板美观度
- 推荐可信度

因此需要从四层降低拍摄影响：

```text
拍摄引导
→ 自动质检
→ 图片标准化
→ 用户确认纠错
```

---

## 8. 拍摄引导设计

### 8.1 衣物拍摄模式

相机页应提供轻提示：

```text
请尽量单件拍摄
放在纯色背景上
光线充足
衣服尽量展开
避免手部遮挡
让衣服尽量填满框内区域
```

### 8.2 分品类提示

| 品类 | 拍摄建议 |
|---|---|
| 上衣 | 平铺或悬挂，正面完整展开 |
| 下装 | 避免折叠，裤脚尽量完整 |
| 外套 | 建议悬挂或平铺，袖子展开 |
| 连衣裙 | 尽量拍完整长度 |
| 鞋 | 左右鞋并排，避免强阴影 |
| 包 | 正面图优先，保留轮廓 |

### 8.3 轻量实时检测

拍摄时可检测：

- 是否太暗
- 是否太糊
- 主体是否太小
- 是否疑似多件衣服
- 背景是否过于复杂
- 是否被手部或杂物遮挡

提示示例：

```text
这张有点暗，可能影响颜色识别。建议换个光线更好的地方。
```

不要强制阻止用户继续，应提供：

```text
继续使用 / 重新拍摄
```

## 9. 图片自动质检

### 9.1 质检指标

| 指标 | 说明 | 处理方式 |
|---|---|---|
| blur_score | 模糊程度 | 低于阈值提示重拍 |
| brightness_score | 明暗程度 | 过暗/过曝提示 |
| subject_area_ratio | 衣物主体占画面比例 | 主体太小提示靠近 |
| background_complexity | 背景复杂度 | 复杂时优先分割 |
| multi_item_score | 多件衣物概率 | 提示是否只导入其中一件 |
| occlusion_score | 遮挡程度 | 高遮挡提示重拍 |
| color_confidence | 颜色置信度 | 低置信度要求用户确认 |

### 9.2 质检结果

每张图片保存：

```json
{
  "quality_score": 0.82,
  "quality_flags": ["low_light", "complex_background"],
  "recommended_action": "confirm_color"
}
```

## 10. 图片标准化处理流程

### 10.1 标准流程

```text
原图上传
→ EXIF 方向修正
→ 文件压缩
→ 尺寸标准化
→ 主体检测
→ 自动裁剪
→ 背景分割
→ 生成透明 PNG
→ 轻微白平衡 / 曝光修正
→ 生成缩略图
→ 保存视觉资产
```

### 10.2 输出资产

每件衣物建议保留：

| 字段 | 用途 |
|---|---|
| original_image_url | 原图，便于重跑模型和追溯 |
| normalized_image_url | 标准展示图 |
| thumbnail_url | 列表缩略图 |
| cutout_image_url | 拼搭板主要素材 |
| mask_url | 分割结果，可选 |
| quality_score | 图片质量评分 |

### 10.3 颜色修正原则

颜色是推荐关键字段，但照片颜色易受光线影响。

建议流程：

```text
模型识别颜色
→ 输出候选颜色
→ 用户确认
→ 确认后的颜色成为正式推荐字段
```

确认页示例：

```text
系统识别：米白色
是否正确？
[白色] [米白] [浅灰] [其他]
```

## 11. Outfit Board 生成流程

### 11.1 输入

```json
{
  "outfit_id": "uuid",
  "outfit_type": "fast",
  "style_profile": {
    "style_tags": ["minimal", "commute"],
    "preferred_colors": ["black", "white", "beige"]
  },
  "items": [
    {
      "item_id": "top_1",
      "role": "top",
      "cutout_image_url": "https://..."
    }
  ]
}
```

### 11.2 处理

```text
选择模板
→ 加载单品抠图
→ 根据 role 布局
→ 调整尺寸与层级
→ 添加标题、标签、推荐理由摘要
→ 导出 outfit_board_image_url
→ 写入 outfit_visual_assets
```

### 11.3 输出

```json
{
  "visual_type": "outfit_board",
  "image_url": "https://cdn.example.com/outfits/uuid/board.png",
  "generation_status": "ready",
  "template_id": "minimal_commute_v1"
}
```

## 12. 生图能力的使用边界

### 12.1 不建议

```text
每次生成推荐时，把所有候选衣物图片都传给多模态 LLM 生成穿搭图。
```

原因：

- 慢
- 贵
- 难缓存
- 容易改变衣服事实
- 生成结果与真实衣物不一致时会伤害信任

### 12.2 建议

```text
真实衣物图 + 抠图拼搭板 + 风格化模板 + 用户主动触发生图
```

### 12.3 允许的生成式增强

| 能力 | 是否推荐 | 说明 |
|---|---|---|
| 生成背景 | 推荐 | 不改变衣服本体，成本可控 |
| 生成版式 | 推荐 | 可做风格化海报 |
| 生成穿搭氛围图 | 可选 | 需标注参考图 |
| 用户上身虚拟试穿 | 后置 | 需要用户授权全身照 |
| 默认三套全部生图 | 不推荐 | 成本和失真风险高 |

## 14. API 补充建议

### 14.1 获取衣物视觉资产

```http
GET /v1/wardrobe-items/{item_id}/images
```

### 14.2 生成 Outfit Board

```http
POST /v1/recommendations/outfits/{outfit_id}/visual-assets
```

Request：

```json
{
  "visual_type": "outfit_board",
  "template_id": "auto"
}
```

Response：

```json
{
  "asset_id": "uuid",
  "status": "queued"
}
```

### 14.3 查询视觉资产状态

```http
GET /v1/outfit-visual-assets/{asset_id}
```

### 14.4 请求虚拟试穿

```http
POST /v1/recommendations/outfits/{outfit_id}/try-on
```

约束：

- 用户必须主动触发
- 用户必须授权使用人体图
- 结果必须缓存
- 前端必须展示“仅供参考”提示

## 15. 成本控制策略

### 15.1 一次性处理

衣物入库时完成：

```text
图片标准化
背景移除
属性识别
embedding 生成
```

推荐时不重复处理原图。

### 15.2 推荐时使用轻数据

推荐模型输入应以结构化数据为主：

```json
{
  "user_style_profile": {
    "style_tags": ["minimal", "commute"],
    "preferred_colors": ["black", "white", "beige"]
  },
  "candidate_items": [
    {
      "item_id": "uuid",
      "category": "top",
      "color": "white",
      "style_tags": ["classic"],
      "location": "main_closet",
      "status": "wearable"
    }
  ],
  "context": {
    "time_left_minutes": 45,
    "scene": "commute"
  }
}
```

不要每次推荐都把衣物图片发送给 LLM。

### 15.3 缓存策略

| 资产 | 缓存方式 |
|---|---|
| cutout image | 按 item_id 长期缓存 |
| thumbnail | 按 item_id 长期缓存 |
| outfit board | 按 outfit_id + template_id 缓存 |
| generated preview | 按 outfit_id + style_profile_hash + prompt_hash 缓存 |
| virtual try-on | 按 outfit_id + body_image_hash + garment_hash 缓存 |

## 17. 结论

Aidrobe 的穿搭展示核心不应该是：

```text
让 AI 画一张好看的图。
```

而应该是：

```text
用用户真实拥有的衣服，生成一张可信、好看、可执行的穿搭决策图。
```

因此推荐路线是：

```text
真实单品图
→ 抠图拼搭板
→ Style Profile 风格化展示
→ 用户主动触发的生图 / 虚拟试穿
```

这条路线更符合 Aidrobe 的产品本质：

> 不是制造一个虚拟时尚幻觉，而是让真实衣橱每天更好地服务用户生活。
