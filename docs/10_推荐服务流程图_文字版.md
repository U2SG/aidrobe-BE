# 推荐服务流程图（文字版）

## 1. 文档目标

把 V1 的推荐服务拆成一条可实现的服务链路，明确推荐生成、排序、落库、推送与反馈回流的流程。

---

## 2. V1 推荐原则

V1 不追求最强时尚智能，先确保：

1. 推荐基于用户真实衣橱
2. 只推荐当前可穿的衣物
3. 给出的方案能够被执行
4. 每天稳定产出 3 套有差异的方案
5. 用户反馈能回流到下一轮排序

---

## 3. 输入与输出

### 输入
- 用户设置：预计出门时间、推送开关
- 衣橱数据：衣物品类、状态、位置、颜色、基础风格标签
- 历史行为：最近穿过什么、喜欢过什么、跳过什么
- 系统规则：通勤默认正式度、最低件数要求

### 输出
- 1 份每日推荐任务
- 3 套穿搭方案：最稳妥 / 最省时间 / 更有变化
- 每套方案的说明文案与排序分数

---

## 4. 总体流程图

```text
定时任务触发
  -> 拉取需要生成推荐的用户
  -> 检查用户设置与最低衣物件数
  -> 获取可穿衣物池
  -> 规则过滤
  -> 候选穿搭生成
  -> 候选方案打分
  -> 去重与多样化
  -> 选出 3 套最终方案
  -> 生成解释文案
  -> 落库 daily_recommendations / outfits / outfit_items
  -> 触发推送
  -> 用户查看 / 选择 / 反馈
  -> 行为写回 wear_history / outfit_feedback
  -> 下一轮排序更新
```

---

## 5. 详细流程

## 5.1 触发阶段

### 触发方式
- 每日定时任务
- 用户手动刷新（可选）
- 导入大量衣物后的重算（可选）

### 定时建议
- 以用户预计出门时间为锚点
- V1 可在出门前 3 小时统一生成并推送

### 触发条件
- 推送开启
- 用户设置了出门时间
- 用户衣橱达到最低推荐条件

---

## 5.2 用户筛选阶段

### 处理逻辑
对所有用户先做轻量过滤：
- 是否存在有效设置
- 是否有足够可穿衣物
- 当天是否已生成推荐

### 最低件数建议
- 上衣 >= 5
- 下装 >= 3
- 外套 / 鞋可选

### 输出
- 待生成推荐的用户列表

---

## 5.3 可穿衣物池构建

### 数据来源
从 `wardrobe_items` 中选取：
- `status = wearable`
- `deleted_at is null`

### 可带入字段
- category / sub_category
- color_main / color_secondary
- style_tags
- formality_score
- location
- latest_worn_at

### 输出
按品类分组的衣物池：
- tops
- bottoms
- outerwears
- dresses
- shoes

---

## 5.4 规则过滤阶段

### 目标
先排除明显不适合参与搭配的衣物或组合。

### 基础规则
1. 只使用可穿衣物
2. 裙装与下装不同时出现
3. 没有主单品的组合不参与
4. 同一件衣物一天内最多出现在有限数量方案中
5. 最近高频穿着衣物适度降权

### V1 不建议过度复杂化
- 暂不加入天气和日程
- 暂不做复杂风格冲突判断

---

## 5.5 候选穿搭生成阶段

### 目标
生成足够多的候选，再从中筛出最优解。

### 基础组合模板
#### 模板 A：上衣 + 下装
适合普通通勤基础方案

#### 模板 B：上衣 + 下装 + 外套
适合更完整的通勤造型

#### 模板 C：连衣裙 + 外套（若有）
适合裙装用户

#### 模板 D：上衣 + 下装 + 鞋
适合图卡展示更完整

### 生成方式建议
- 先按品类笛卡尔积生成初步组合
- 再用简单规则删掉明显不合理组合
- 控制候选量，避免组合爆炸

### 候选量建议
单用户每日保留 20~50 个候选即可

---

## 5.6 候选打分阶段

### 总分公式建议
```text
total_score =
  style_score * 0.35 +
  execution_score * 0.35 +
  preference_score * 0.20 +
  freshness_score * 0.10
```

### 1. style_score（搭配分）
考虑：
- 基础颜色协调
- 品类组合合理性
- 通勤正式度大体匹配

### 2. execution_score（可执行分）
考虑：
- 是否全部可穿
- 存放位置是否集中
- 是否需要额外准备动作（V1 用状态近似）

### 3. preference_score（偏好分）
考虑：
- 用户最近点赞过的颜色/品类/风格
- 用户过去常选中的单品特征

### 4. freshness_score（新鲜感分）
考虑：
- 最近 3 天是否穿过相同主单品
- 最近 7 天是否重复相似组合

---

## 5.7 多样化与最终选 3 套

### 目标
避免 3 套看起来几乎一样。

### 处理方法
1. 按总分降序排序
2. 选第 1 套作为最稳妥
3. 第二套尽量与第一套主单品不同，作为最省时间
4. 第三套在可接受范围内提高变化感，作为更有变化

### 推荐类型映射建议
- `safe`：分数整体最稳，风险最低
- `fast`：执行分最高
- `stylish`：在不离谱前提下更有变化

---

## 5.8 解释文案生成

### 目标
告诉用户“为什么推荐”，而不是只给一个结果。

### 文案输入
- 方案类型
- 核心单品
- 可执行特点
- 位置 / 状态信息

### 生成策略
V1 建议：
- 规则模板优先
- LLM 只做润色，不做核心决策

### 模板示例
- 最稳妥：适合普通通勤场景，主衣柜可直接拿取
- 最省时间：不需要熨烫，搭配简单，适合赶时间时穿
- 更有变化：在通勤得体的基础上更有层次感

---

## 5.9 落库阶段

### 写入表
- `daily_recommendations`
- `outfits`
- `outfit_items`

### 关键点
- 确保一个用户一天只存在一份主推荐结果
- 保留打分字段，方便后续分析推荐质量

---

## 5.10 推送阶段

### 触发条件
- 推荐生成成功
- 用户开启推送

### 文案建议
- 今天有 3 套可直接执行的穿搭，出门前看一下
- 如果赶时间，这里有一套最省时间的方案

### V1 原则
- 每天最多一次主推送
- 不做多轮追推

---

## 5.11 用户行为回流阶段

### 可能行为
- 打开推荐页
- 查看详情
- 选择“今天穿这套”
- 点赞 / 点踩
- 跳过

### 写回表
- `wear_history`
- `outfit_feedback`

### 回流用途
- 更新偏好分
- 降低重复推荐
- 识别“点了喜欢但从不穿”和“常穿但不点赞”的差异

---

## 6. 异常与兜底流程

## 6.1 衣物不足

### 条件
不满足最低件数要求

### 返回状态
`insufficient_items`

### 前端展示
- 再录入 3 件上衣和 2 件下装，就能开始生成推荐

---

## 6.2 候选不足

### 条件
过滤后候选数过少

### 处理方式
- 放宽部分非关键规则
- 降低多样化要求
- 必要时仅返回 1~2 套

---

## 6.3 推荐生成失败

### 返回状态
`failed`

### 处理方式
- 保留错误日志
- 支持后台重试
- 前端提示稍后重试，同时显示衣橱入口

---

## 7. 服务拆分建议

### 推荐实现最小拆分
1. **App 服务**
   - 提供用户设置、衣橱、推荐查询接口
2. **推荐任务服务**
   - 负责定时触发、用户筛选、结果落库
3. **推荐引擎模块**
   - 负责规则过滤、候选生成、打分排序
4. **文案生成模块**
   - 负责解释文案模板或 LLM 润色

### V1 可以先不拆微服务
- 逻辑上拆模块即可
- 部署上可仍在一个后端服务内完成

---

## 8. 推荐链路伪代码

```text
for user in users_to_generate:
    settings = get_user_settings(user)
    if not valid(settings):
        continue

    items = get_wearable_items(user)
    if not enough(items):
        save_status(user, insufficient_items)
        continue

    candidates = build_candidates(items)
    candidates = apply_rules(candidates)

    if len(candidates) == 0:
        save_status(user, failed)
        continue

    scored = score_candidates(candidates, user_history)
    diversified = diversify(scored)
    final_outfits = pick_top3(diversified)
    final_outfits = add_reason_text(final_outfits)

    save_recommendations(user, final_outfits)
    push_notification_if_needed(user)
```

## 9. V1 与 V2 的边界

### V1
- 规则驱动推荐
- 结构化字段打分
- 模板式解释文案

### V2
- 接入天气
- 接入工作日场景
- 更细的取衣成本
- 更强的用户偏好学习
- 多轮提醒

---

## 10. 一句话总结

V1 的推荐服务不是“让大模型自由穿搭”，而是：

**先用规则和结构化字段生成稳定候选，再用轻量智能做排序和解释，确保每天都能给出用户现实可执行的 3 套方案。**
