# 文档评审报告：Aidrobe API Guide 与 V4 架构升级建议

> 文档版本：V1.0  
> 评审对象：`user-guide(1).md`、`粘贴的 markdown (1)。md`  
> 评审目的：判断当前文档是否足以支撑 iOS MVP、后端开发、算法迭代与后续 V4 产品白皮书。

---

## 1. 总体评价

当前两份文档已经形成了比较好的工程雏形：

- `user-guide(1).md` 更像一份 **后端 API 使用指南**，覆盖认证、用户设置、图片上传、导入任务、衣橱、推荐、反馈、风格灵感、错误码与完整用户流程。
- `粘贴的 markdown (1)。md` 更像一份 **架构升级评审意见**，重点指出了同步识别、链接导入、location、风格来源、批量学习、任务状态等关键缺口。

两者的关系可以理解为：

```text
user-guide(1).md = 当前 V1/V1.5 API 草案
粘贴的 markdown (1)。md = 面向 V2/V4 的架构升级建议
```

结论：

> 当前文档已经能支撑一个早期 MVP，但如果目标是做成“异步内容摄取 + 多模态衣物识别 + 个人风格学习 + 场景化穿搭决策”的产品，需要把第二份文档中的设计吸收进主文档体系，并进一步产品化。

---

## 2. 结构完整性评审

### 2.1 优点

`user-guide(1).md` 的结构比较完整，已经具备一份 API 使用文档的基本要素：

- 通用响应格式
- 认证方式
- 图片直传 OSS
- 导入任务
- 衣橱管理
- 今日推荐
- 穿搭记录与反馈
- 风格灵感
- 错误码
- 完整流程示例

这对 iOS 客户端开发非常友好，因为客户端可以从登录、上传、导入、确认、推荐、反馈走完整闭环。

### 2.2 主要缺口

现有文档仍然偏“接口清单”，缺少以下四类产品工程文档：

1. **状态机文档**
   - import task 状态流转
   - style source 学习状态流转
   - recommendation 生成状态与缓存状态

2. **异步任务说明**
   - 队列、重试、防抖、失败兜底
   - 客户端轮询 / SSE / APNs 策略

3. **数据模型说明**
   - wardrobe item 与 external source、style source、outfit、feedback 的关系
   - 原图、标准图、embedding、结构化标签之间的关系

4. **产品目标和策略说明**
   - 为什么这样设计
   - 哪些接口是 V1，哪些是 V4
   - 哪些设计是为了竞品差异化

## 3. 逻辑自洽性评审

### 3.1 当前逻辑自洽的部分

当前 API 主链路是自洽的：

```text
登录
→ 设置出门时间
→ 获取上传地址
→ 上传图片
→ 创建导入任务
→ 确认入库
→ 获取今日推荐
→ 记录穿着
→ 提交反馈
→ 上传风格灵感
```

这条链路能跑通早期 MVP，尤其适合验证：用户是否愿意录入衣服、是否愿意看推荐、是否愿意反馈。

### 3.2 当前逻辑不够自洽的部分

#### 问题一：导入任务名为 task，但行为仍是同步接口

当前文档中 `POST /v1/import-tasks` 被描述为“调用后后台立即进行 Vision API 识别，同步返回识别结果”。这在命名上叫 task，但产品行为上更像同步识别 API。

风险：

- 图片识别、链接抓取、LLM 补全都可能耗时
- 客户端等待时间不可控
- 链接导入失败重试难以表达
- 无法自然支持批量上传、PDF、视频封面、商品链接等复杂输入

建议：

```text
POST /v1/import-tasks → 202 Accepted
GET /v1/import-tasks/{task_id} → 查询进度
POST /v1/import-tasks/{task_id}/confirm → 用户确认入库
```

#### 问题二：source_url 被预留，但不是一等流程

文档中已经有 `source_url` 字段，但缺少链接解析流程。它应该被升级为一等能力：

```text
source_url
→ 短链解析
→ 平台识别
→ metadata / og:image / 商品主图提取
→ 截图兜底
→ Vision + LLM 抽取
→ candidate item
```

#### 问题三：location 已进入衣橱表，但没有进入导入确认页

衣服的现实存放位置是产品差异化关键之一。如果用户确认入库时没有填写 `location`，后续“赶时间优先主衣柜”的推荐就无法成立。

建议将 `location` 从普通可选字段提升为导入确认页的核心字段。

#### 问题四：Style Profile 仍停留在 inspiration image

当前 Style Profile 主要支持上传灵感图和风格标签，但用户真实需求是“甩链接、甩截图、甩杂志、甩多图，让系统学习我的风格”。因此应该抽象为统一的 `style_sources`：

```text
image / image_batch / link / screenshot / pdf / magazine / shared_content
```

## 4. 技术可落地性评审

### 4.1 已经具备工程可落地基础

当前方案中的以下设计是合理的：

- 图片预签名上传，客户端直传对象存储
- API 服务只保存 file_url / object_key
- 今日推荐通过缓存返回，避免每次实时生成
- 推荐触发有防抖机制
- 衣物更新、删除、导入确认后触发推荐重算
- 登录使用 Apple Sign In，符合 iOS 产品起步路径

### 4.2 必须补强的工程能力

#### 异步任务系统

建议后端引入：

```text
API Server
→ import_tasks / style_sources
→ Redis Queue / Celery / RQ / Dramatiq / Arq
→ Vision Worker / Link Parser Worker / LLM Worker / Recommendation Worker
→ DB + Object Storage + Vector DB
```

#### 多来源内容解析

建议将导入统一成：

```text
input_type = image / link / screenshot / shared_content / pdf / image_batch
source_type = camera / album / taobao / jd / xhs / douyin / web / receipt / manual
```

#### 可解释推荐

推荐结果不应该只返回标题和原因，还应该返回关键评分项，至少内部可见：

```json
{
  "utility_score": 0.86,
  "time_cost_score": 0.91,
  "aesthetic_score": 0.72,
  "freshness_score": 0.66,
  "weather_score": 0.80
}
```

## 5. 产品定位清晰度评审

当前 API 文档本身没有明确产品定位，这是正常的，因为它是工程文档。但从接口设计反推，产品定位已经比较清楚：

> Aidrobe 不是泛衣橱管理工具，而是围绕“出门前穿什么”构建的 AI 穿搭决策系统。

为了让团队协作更稳，建议把产品定位固定成：

```text
Aidrobe 是一个基于真实衣橱、现实状态、时间压力和个人审美的 AI 出门穿搭决策助手。
```

这个定位比“AI 衣橱 App”更强，因为它强调：

- 真实衣橱
- 现实状态
- 时间压力
- 个人审美
- 出门决策

---

## 6. 差异化价值评审

当前方案最有潜力形成差异化的点有四个：

### 6.1 现实可执行性

竞品大多关注“衣橱可视化”和“穿搭灵感”，Aidrobe 可以进一步强调：

```text
这套衣服不仅好看，而且现在找得到、拿得到、来得及穿。
```

### 6.2 时间敏感推荐

`safe / fast / stylish` 与 `relaxed / standard / rushed / instant` 这组设计非常好，应该成为产品核心表达。

### 6.3 多来源导入

从拍照、链接、截图、分享扩展、订单截图、PDF、杂志中提取衣物与风格，是降低建库门槛的关键。

### 6.4 风格学习

用户不用写长文本，只要甩图、甩链接、点赞、不喜欢，系统就逐步学习她的真实审美。

---

## 7. 主要风险与建议

| 风险 | 说明 | 建议 |
|---|---|---|
| 录入成本高 | 用户不愿意拍完整衣柜 | 引入链接、截图、分享、receipt forwarding、批量上传 |
| 同步识别阻塞 | 图片/链接/LLM 都可能慢 | 全面异步任务化 |
| 推荐看似合理但不可执行 | 衣服找不到、待洗、需熨烫 | location + status + time_cost 必须入推荐模型 |
| 风格学习黑盒 | 用户不知道系统学到了什么 | 每个 style source 展示“学习中/已学习/学到了什么” |
| 平台链接不稳定 | 淘宝/小红书/抖音解析经常变化 | adapter + fallback：metadata、截图、用户补图 |
| 生图破坏信任 | 生成图可能篡改真实衣物 | V4 之前只做真实单品图与拼搭板，虚拟试穿作为可选增强 |

---

## 8. 结论

两份文档合并后，最应该形成的升级方向是：

```text
从“API 可跑通的衣物识别 MVP”
升级为
“异步多来源内容摄取 + 真实衣橱建模 + 时间敏感推荐 + 风格学习闭环”的 V4 产品系统。
```

建议下一步将主文档拆成三条线：

1. 产品白皮书：讲愿景、差异化、商业价值。
2. 技术白皮书：讲系统架构、任务队列、模型链路、数据模型。
3. API Guide V2：讲接口、状态机、错误码、客户端接入细节。
