# V1 范围精简方案（V1 Slim）

## 1. 文档目标

在现有 `03_整体PRD_MVP.md` 的基础上，给出一个更薄的 V1 范围，供小团队（1~3 人）在 4~6 周内实际跑完 MVP 验证闭环。  
与原 V1 的关系：本方案是原 V1 的**子集**，不是替代。等 V1 Slim 验证通过后，再把原 V1 剩余能力作为 V1.1 / V1.2 补齐。

---

## 2. 核心判断

### 2.1 我们在验证什么
不是：用户是否喜欢 AI 穿搭。  
而是：**用户是否愿意在早晨打开 App 看一眼今天穿什么，并采纳其中一套。**

### 2.2 不验证的
- 多种导入方式的转化差异（一种能用即可）
- 识别准确率（V1 Slim 不追求高精度，允许用户轻改）
- 多场景感知（先只做通勤默认场景）
- 推送多轮策略（先不做推送，靠用户主动打开）

### 2.3 为什么要再砍
原 V1 的 10 个页面 + 完整 API + 完整 DB + 分享扩展 + 链接解析 + 图像识别链路，6~8 周对小团队偏紧。  
大多数 MVP 死在“想验证的东西太多，每样都做得半拉子”，不是死在功能少。

---

## 3. V1 Slim 的范围

## 3.1 保留（P0，必须有）

### 导入
- **拍照 / 相册导入**（唯一入口）
- 图片上传到对象存储
- 服务端调用**托管视觉 API**（如 GPT-4V / 豆包视觉 / 通义千问 VL）识别 `category` + `color_main` 两个字段
- 导入确认页：用户可编辑品类、颜色、名称（其他字段全部可选）

### 衣橱
- 衣橱列表页（单列或双列卡片）
- 衣物详情页
- 状态切换：**只有两态** `可穿` / `暂不可用`
- 删除

### 推荐
- 今日推荐页
- 3 套方案（`safe` / `fast` / `stylish`）
- **小衣橱友好**：即使只有 3 件，也尽力给出至少 1 套；给不出时展示“再加一件下装就能搭”的引导，而不是空状态
- 三套方案**主单品必须不重合**（硬约束）
- **"打开即有"生成策略**（见下文 §3.1.1）：不允许任何 loading 空屏
- 推荐理由用**模板生成**（不调 LLM）

### 3.1.1 "打开即有"的触发链路（V1 Slim 版）

#### 核心原则
用户打开 App 的任何时刻，推荐都已经在那里。没有 loading、没有"正在生成"。

#### 三条触发链路
1. **预生成（主）**：`departure_time - 90 分钟`自动生成当日推荐
2. **夜间兜底**：凌晨 03:00 对未设 `departure_time` 的用户批量生成，保底一份
3. **衣橱变更触发**：用户新增 / 删除 / 改状态 → 异步重算当天推荐，用户下次打开时看到更新版

#### 如果用户在预生成前打开
- **立即返回昨日推荐或兜底版**（绝不返回空）
- 后台同步触发一次快速重算
- 重算完成后用"下拉刷新/轻提示"告诉用户"今日推荐已更新"

#### 时间富裕度（V1 Slim 简化版）
- V1 Slim 先不做分档，所有用户统一返回"标准档"三套
- 但界面上必须显示"距离出门 XX 分钟"的倒计时，让用户自己感知时间紧张度
- V1.1 再引入按剩余时间分档的候选池筛选（宽裕 / 标准 / 紧张 / 极速）

### 反馈与历史
- “今天穿这套”按钮
- 喜欢 / 不喜欢 二选一（不做原因标签）
- 本地记录 `wear_history`，用于推荐去重

### 设置
- 出门时间（单字段，用于 1）倒计时展示 2）预生成触发锚点，V1 Slim 不触发推送）

## 3.2 推迟到 V1.1

- 链接导入 / 分享扩展 / 截图导入
- 推送通知
- 按剩余时间富裕度分档的候选池筛选（V1 Slim 全员标准档）
- 前夜预演版（22:00 生成次日预备版）
- 反馈原因标签（too_formal / too_complex / not_me / not_for_today）
- 衣物位置字段（location）
- 季节标签、风格标签、正式度评分
- 编辑衣物页（V1 Slim 只做“详情页内联编辑”）
- 历史记录页
- Onboarding 多步引导（V1 Slim 用一屏价值说明 + 直接进添加衣物）

---

## 3.3 推迟到 V2 及以后（与原路线保持一致）
- 天气接入
- 场景感知（注：若 V1 Slim 第三周发现用户大量反馈“场景不对”，可紧急把场景快切从 V2 前置到 V1.1）
- 重复穿搭降权
- 取衣成本建模
- 外部灵感导入
- 风格聚类

## 6. 数据表精简

### 保留
- `users`（简化：只有 id / created_at）
- `user_settings`（只有 departure_time）
- `wardrobe_items`（status 只两态；location 字段保留但不强制填；季节/风格/正式度字段预留但 V1 Slim 不写入）
- `wardrobe_item_images`（只保留 `original` + `standard`）
- `import_tasks`（task_status 只有 `waiting_confirm` / `completed` / `failed` 三态；V1 Slim 识别同步完成，pending/parsing 直接跳过）
- `daily_recommendations`
- `outfits`
- `outfit_items`
- `outfit_feedback`
- `wear_history`

### 推迟
- `external_sources`（无外部导入）
- `item_embeddings`（V1 Slim 不做向量召回，纯规则）
- `operation_logs`
- `item_tags`

## 7. 推荐引擎精简

### V1 Slim 推荐策略
```text
1. 拉取 status=wearable 的衣物
2. 如果总件数 < 3：返回 insufficient_items + 引导文案
3. 如果上衣 + 下装都有：按品类笛卡尔积生成候选
   否则：按现有品类尽力组合（可能只有 1~2 套）
4. 打分维度简化为 2 个：
   - 颜色协调度（硬编码颜色冲突表）
   - 新鲜度（最近 3 天穿过的主单品降权）
5. 三套主单品必须不重合
6. 理由文案用模板：
   - safe: "经典颜色搭配，适合日常通勤"
   - fast: "你最近常穿的单品，省时间"
   - stylish: "换个风格试试：{主单品特征}"
```

### 不做
- LLM 润色（V1.1 再加）
- 用户偏好学习（V1 Slim 反馈数据只用于“不喜欢=降权”）
- 位置打分
- 正式度打分
- embedding 召回

## 8. 技术栈精简

### 客户端
- iOS 原生 SwiftUI
- 只集成系统相机 / 相册 / HTTP 客户端
- 不做分享扩展

### 服务端
- Python FastAPI（与仓库 Python 定位一致）
- PostgreSQL（不引入 pgvector）
- 对象存储（S3 兼容即可，测试阶段可用 MinIO）
- 视觉识别：**直连托管 API**（GPT-4V 或国内替代），不自建模型服务

### 任务系统
- V1 Slim 不需要完整消息队列
- 识别同步完成（单次 2~4 秒用户可以等）
- 预生成 / 兜底 / 衣橱变更触发用**轻量方案**：
  - `APScheduler`（Python 进程内调度）承担定时任务
  - `FastAPI BackgroundTasks`承担衣橱变更后的异步重算
  - 规模放大到 V1.1+ 再考虑换 Celery / RQ + Redis

## 10. V1 Slim 验收标准

### 功能合格
- 新用户可 5 分钟内录完 5 件衣物并看到推荐
- 3 件衣物即可触发至少 1 套推荐（不是空状态）
- 推荐 3 套主单品无重复
- "今天穿这套"次日不会再推相同主单品
- **打开即有**：任何时间打开 App，首屏都不出现 loading 占屏（允许底部"已更新"轻提示）

### 指标观测（不是硬合格线，只是观测）
- D1 留存
- D7 留存
- 人均录入件数中位数
- 推荐采用率（今天穿这套 / 推荐打开）
- 喜欢率

## 11. V1 Slim 与原 V1 的关系

```text
V1 Slim (4~6 周)
  ↓ 验证通过
V1.1：补链接 / 分享 / 推送 / 历史 (2~3 周)
  ↓
V1.2：补 embedding / LLM 文案 / 偏好学习 (2~3 周)
  ↓
V2：天气 + 场景 + 取衣成本
  ↓
V3：外部灵感 + 风格画像
```

---

## 12. 一句话总结

**V1 Slim 不是在做一个 AI 衣橱 App，而是在验证“早晨有人愿意打开它看一眼”这件事是否成立。**  
功能做得越少，这个问题的答案越清晰。
