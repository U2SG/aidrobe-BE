# 已识别风险与待决策点

## 1. 文档目标

在进入研发前，集中记录当前文档在产品、技术、运营层面已暴露的薄弱点与需要团队决策的开放问题。  
本文不作为设计结论，仅作为 M1（PRD + 技术评审）的讨论输入清单。

---

## 2. 产品层面

## 2.1 建库冷启动门槛被低估

### 问题
- `03_整体PRD_MVP.md` §13、`10_推荐服务流程图_文字版.md` §5.2 要求“上衣 ≥ 5 + 下装 ≥ 3”才生成推荐
- 实际下载当晚多数用户只会录 2~3 件
- 第二天打开推荐页为 `insufficient_items`，基本流失

### 建议决策方向
- V1 就要提供“衣橱不足也能用”的过渡体验
- 哪怕只有 3 件，也要能给出 1 套带解释的推荐，而不是空状态
- 把“录 ≥ 15 件”作为留存目标，而不是推荐生效门槛

---

## 2.2 `status` / `location` 字段极易成为僵尸字段

### 问题
- 5 个状态（可穿 / 待洗 / 已洗未收 / 需熨烫 / 暂不使用）要求用户主动维护
- 真实用户不会每天切换这些状态
- 不维护则 `execution_score` 信号失真，反而不如不要

### 建议决策方向
- V1 砍到 2 态：`可穿` / `暂不可用`
- `location` 从必填改为可选，不参与 V1 打分
- 改用隐式信号：`latest_worn_at`（已穿过当天不再推荐）

---

## 2.3 三套推荐在小衣橱下会塌缩成同一套

### 问题
- 10 件衣服规则过滤后候选可能只有 4~6 个
- 按总分排 top3，容易出现“三套共享 80% 单品，只换鞋”
- 用户感知是“就这一套换着给我看”

### 建议决策方向
- `10_推荐服务流程图_文字版.md` §5.7 加硬约束：三套方案的主单品（上衣 / 连衣裙）必须完全不重合
- 宁可牺牲第三套的总分，也要保证“看起来有三种选择”
- 小衣橱（<15 件）下，第三套分数阈值可以降低

---

## 2.4 推荐触发时机与"打开即有"的平衡

### 产品初心（不可妥协）
> **用户打开 App 的那一刻，推荐必须已经在那里。**  
> 看到 loading 就已经破功了——这是"决策外包"心智的一部分。

所以"完全惰性生成"不可取。但"出门前 3 小时生成"又太早，内容容易僵化。  
正确的做法是把问题拆成两个独立的维度：

### 维度一：何时生成（保证打开即有）

#### 触发策略组合
1. **主策略 — 预生成**
   - 锚点：用户的 `departure_time`
   - 生成时间：`departure_time - 90 分钟`
   - 原因：90 分钟覆盖了绝大多数"醒来→出门"的窗口，又不会提前到前夜
2. **兜底策略 — 夜间批处理**
   - 每天 03:00 对未设置 `departure_time` 或 `departure_time < 05:30` 的用户批量生成
   - 避免凌晨/极早出门用户打开时无结果
3. **衣橱变更触发**
   - 用户新增、删除、改状态 → 使当天缓存失效 → 下次打开时已由后台重算完成
4. **提前打开触发**
   - 若用户在预生成时间前打开 App：仍返回**已有的昨日兜底推荐 + 快速重算**，而不是返回 loading
   - 重算完成后通过"下拉刷新/轻提示"告诉用户"今日推荐已更新"
5. **前夜预演（可选，V1.1+）**
   - 晚上 22:00 生成一份"预备版"，用户睡前打开也能看到
   - 次日 `departure_time - 90 分钟`再更新为正式版

#### 核心原则
- 任何时刻打开 App，都能立即看到一份推荐（哪怕是昨日兜底版或预备版）
- 推荐可能会"变得更新鲜"，但不会"从无到有"

### 维度二：时间富裕度作为推荐输入

用户在"还有 2 小时出门"和"还有 15 分钟出门"时，需要看到的**不是同一套**推荐。  
但这属于**推荐引擎内部的输入变量**，不属于触发逻辑。

#### 富裕度分档（建议）
| 剩余时间 | 档位 | 推荐内容特征 |
|---|---|---|
| > 90 分钟 | 宽裕 | 可以推需要熨烫、叠穿、稍复杂的方案；可以多样化到 stylish 路线 |
| 30~90 分钟 | 标准 | 标准三套（safe / fast / stylish） |
| 15~30 分钟 | 紧张 | 三套都偏 fast；过滤掉需要熨烫、需去收纳箱取的单品 |
| < 15 分钟 | 极速 | 只给 1 套"开门即穿"方案，去掉 stylish 档 |

#### 实现方式
- 推荐**候选池**在预生成时就全量打好分
- 用户打开 App 时，根据**当下**到 `departure_time` 的剩余时间，从候选池动态筛选和排序
- 这样预生成不浪费，时间感知也做到了

### 建议决策方向（整合版）
- V1 采用"预生成 + 夜间兜底 + 衣橱变更触发"三条触发链路
- 明确禁止任何情况下返回空 loading
- 剩余时间富裕度作为推荐引擎的**排序变量**，而非触发变量
- 候选池按富裕度分档预筛可在 V1.1 引入，V1 Slim 先做单档（标准档）

## 2.5 缺少“今日场景 / 心情”输入

### 问题
- `01_版本设计_V1-V3.md` 把“场景感知”放到 V2
- 但常见负反馈就是“今天要见客户 / 出差 / 去探店，推荐不对”
- 再准的算法也猜不到今天的场合变化

### 建议决策方向
- V1 就加一行“今日场景”快捷切换（普通通勤 / 见客户 / 轻松日）
- 不做 AI 理解，只作为权重因子传给现有规则引擎
- 实现成本极低，但能挡住大部分“推得不对”的投诉

---

## 2.6 反馈闭环过度依赖显式行为

### 问题
- `05_模块PRD_衣橱与推荐.md` §9 的反馈均为显式点按
- `10_推荐服务流程图_文字版.md` §5.11 已提到“点喜欢但从不穿” vs “常穿但不点赞”的差异
- 但 V1 没把隐式信号纳入打分

### 建议决策方向
- 显式反馈只用于负反馈（快速降权）
- 正偏好学习主要来源改为 `wear_history.worn_date`（真实穿过）
- “看了没点但重复查看”也作为弱正信号

---

## 2.7 单 iOS 平台策略的风险

### 问题
- 目标用户（20~35 岁女性上班族）Android 占比不低
- iOS 单平台验证假设成立后，Android 移植要重头做

### 建议决策方向
- V1 继续 iOS 优先不变
- 后端从第一天起按“多端可接入”设计（不要把会话 / 分享扩展逻辑耦合进 iOS 私有协议）
- Android 原生 vs Flutter / React Native 的取舍留到 V1 验证通过后再定

## 3. 技术层面

## 3.1 视觉识别模型选型未定

### 问题
- `06_技术方案草案.md` §4 只给出链路，没有具体模型方案
- CLIP / BLIP-2 / GPT-4V / 自训 YOLO + 分类头 成本和精度差异极大
- 直接影响 V1 成本模型

### 建议决策方向
- M1 前补一份《视觉识别模型选型对比》
- 至少覆盖：准召、单次调用成本、延迟、隐私（云端 vs 端侧）四维度
- V1 建议用托管视觉 API 起步（GPT-4V / 豆包 / 通义），识别链路本地化到 V1.1 再考虑

---

## 3.2 LLM 文案成本未建模

### 问题
- 每个用户每天 3 套方案 × 每套一段理由 = 至少 3 次 LLM 调用
- 1 万 DAU 每月 ~90 万次；若用 GPT-4 成本显著
- 文档未明确“LLM 降级到模板”的开关

### 建议决策方向
- V1 模板优先，LLM 只在置信度低或用户点开详情时才润色
- 预算上限写进配置，超限自动降级到模板
- 埋点记录“模板 vs LLM”两类推荐的采用率差异，量化 LLM 价值

---

## 3.3 原图长期留存的合规风险

### 问题
- `06_技术方案草案.md` §2.2 建议保留 `original_image_url`
- 衣物原图可能包含人像、家居背景、地理位置 EXIF
- 生物识别 + 居家隐私双重敏感，影响商店审核和用户信任

### 建议决策方向
- V1 明确原图保留策略：默认保留 90 天，到期自动转为仅保留 `cutout` + embedding
- 上传前在客户端抹除 EXIF
- 用户中心提供“一键删除所有原图”入口

---

## 3.4 链接导入对淘宝 / 京东 / 小红书的真实可用性存疑

### 问题
- 各平台反爬策略持续收紧
- 小红书链接需要 App 解锁短链，外部抓取稳定性差
- V1 文档假定链接解析可行，但没做 PoC 验证

### 建议决策方向
- M1 前先做一轮“链接导入可行性 PoC”，覆盖淘宝 / 京东 / 小红书 / 得物
- 若稳定性 < 70%，V1 链接导入降级为 P1，改主推“分享扩展 + 截图识别”
- 分享扩展走系统级共享，成功率显著高于外部 URL 抓取

## 4. 运营 / 度量层面

## 4.1 MVP 合格线没有数字

### 问题
- `01_版本设计_V1-V3.md` §3.5 列出了推荐打开率 / 采用率 / 7 日留存等指标
- 但没写合格阈值：20% 算成功还是 40%？

### 建议决策方向
- M1 前补指标基线表，至少给出“继续 / 存疑 / 终止”三档阈值
- 参考行业基准：工具类 7 日留存 25% 以上、晨间使用类日均唤起 0.8 次以上

## 4.2 缺退出条件

### 问题
- 若 V1 跑 8 周后采用率只有 5%、衣橱件数中位数只有 4 件，团队继续 V2 还是 pivot？

### 建议决策方向
